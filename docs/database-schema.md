# Схема базы данных (Cloud Firestore)

Этот документ описывает структуру данных сайта-справочника по Elden Ring:
все коллекции/документы Firestore, их поля, связи между ними и — отдельно —
почему схема сделана именно денормализованной (с дублированием данных), а
не в виде классических нормализованных таблиц.

Проект — статический сайт (HTML/CSS/JS) без собственного бэкенда, все данные
хранятся в Cloud Firestore (тариф Spark) и читаются/пишутся напрямую из
браузера через клиентский Firebase SDK. Это определяет часть решений ниже
(например, почему `.select()`-проекций нет — см. раздел «Оптимизация
запросов»).

## Обзор коллекций

| Путь | Тип | Кто читает | Кто пишет |
|---|---|---|---|
| `gameData/eldenring` | документ | все (гости и авторизованные) | только admin |
| `gameData/shadowerdtree` | документ | все | только admin |
| `gameData/translations` | документ | все | только admin |
| `gameData/bossDetails` | документ | все | только admin |
| `gameData/gallery` | документ | все | только admin |
| `siteConfig/main` | документ | все | только admin |
| `users/{uid}` | коллекция документов | владелец документа; админ (только на чтение и только поле `role`) | владелец (кроме `role`); админ (только поле `role`) |

Все документы читаются через `onSnapshot` (real-time слушатели), а не
разовым `.get()` — это относится и к публичным страницам, и к админ-панели.
Любое изменение, сохранённое через админ-панель, поэтому мгновенно
появляется на уже открытых страницах сайта без перезагрузки.

## `gameData/eldenring` и `gameData/shadowerdtree`

Один документ на игру, целиком описывающий список регионов и боссов этой
игры:

```
{
  regions: [
    {
      id: string,              // например "limgrave"
      name: string,            // имя на английском (базовый язык)
      bosses: [
        {
          id: string,          // например "lim-29"
          name: string,
          categories: string[] // подмножество ['story','hard','quest','optional']
        },
        ...
      ]
    },
    ...
  ]
}
```

`categories` — необязательное поле; если у босса ещё нет категорий,
фильтр по категориям на клиенте считает его видимым при любом фильтре
(см. `matchesCategoryFilter` в `scripts/script.js`).

## `gameData/translations`

Переводы имён регионов и боссов на русский (`ru`) и казахский (`kk`).
Английский не хранится отдельно — он берётся прямо из `name` в документах
выше, поэтому для английского языка отдельной записи нет:

```
{
  ru: { regions: { [regionId]: string }, bosses: { [bossId]: string } },
  kk: { regions: { [regionId]: string }, bosses: { [bossId]: string } }
}
```

## `gameData/bossDetails`

Один документ, ключи которого — id боссов. Хранит характеристики и
лор/тактику для тех боссов, для которых это уже заполнено в админ-панели;
для остальных ключ просто отсутствует, и страница босса показывает
плейсхолдер "coming soon":

```
{
  [bossId]: {
    hp: number | null,
    runes: number | null,
    ru: {
      tagline: string,
      description: string,
      location: string,
      attacksIntro: string,
      attacks: string[],
      tactics: string,
      tacticsList: string[],
      notesIntro: string,
      notes: string[],
      loot: [{ name: string, chance: string }],
      trivia: string,
      quote: { text: string, author: string },
      resistances: {
        effects: { [effectLabel]: string },  // Poison, Bleed, Sleep, ...
        damage: { [damageLabel]: string }    // Fire, Holy, Magic, ...
      }
    }
  }
}
```

## `gameData/gallery`

```
{
  photos: [
    { id: string, thumb: string, full: string, game: 'eldenring' | 'shadowerdtree' }
  ]
}
```

Порядок массива — это порядок показа в галерее; админ-панель меняет его
кнопками "вверх/вниз", а не отдельным полем сортировки.

## `siteConfig/main`

Редактируемые тексты сайта (подвал, контакты):

```
{
  footerCredit: string,
  phone: string,
  telegram: string,
  emails: string[]
}
```

## `users/{uid}`

Один документ на аккаунт, id документа = Firebase Auth `uid`:

```
{
  email: string,
  nickname: string,          // необязательно
  avatarDataUrl: string,     // необязательно, data: URL (base64)
  createdAt: Timestamp,
  lastLoginAt: Timestamp,
  progress: string[],        // id побеждённых боссов
  history: [{ id: string, at: number }],  // недавняя активность, новые сверху, максимум 20
  role: 'admin'               // поле присутствует ТОЛЬКО у админов; у обычных
                               // пользователей поле просто отсутствует
}
```

`role` умышленно не выставляется при регистрации (`allow create` в
`firestore.rules` явно запрещает создавать документ уже с этим полем) —
единственный способ получить `role: 'admin'` это либо ручная правка в
консоли Firebase (для самого первого администратора), либо действие уже
существующего администратора в разделе "Users" админ-панели.

## Безопасность (Firestore Security Rules)

Полный файл — `firestore.rules` в корне репозитория. Кратко:

- `gameData/*` и `siteConfig/*` — читать может кто угодно (сайт работает
  для гостей), писать — только пользователь, у чьего `users/{uid}` стоит
  `role == 'admin'`.
- `users/{uid}` — читать и писать большинство полей может только владелец
  документа; поле `role` не может менять сам владелец ни при создании, ни
  при обновлении — это закрывает возможность самому себе через консоль
  браузера дописать `role: "admin"`.
- Администратор дополнительно может: читать любой `users/{uid}` (нужно
  для списка аккаунтов в админ-панели) и менять **только** поле `role`
  любого аккаунта (проверяется через
  `request.resource.data.diff(resource.data).affectedKeys().hasOnly(['role'])`)
  — то есть админ не может от имени другого пользователя поменять его
  никнейм, аватар или прогресс, только выдать/забрать права администратора.

## Почему схема денормализована (а не набор нормализованных таблиц)

Каноническая реляционная схема развела бы данные на отдельные сущности
("регион", "босс", "перевод", "категория") со внешними ключами между
ними. Здесь вместо этого каждый регион хранит вложенный список своих
боссов внутри одного документа игры — то есть данные о боссе физически
дублируются внутри документа его региона, а не лежат в отдельной
коллекции `bosses` со ссылкой на `regionId`.

Это осознанное решение, а не упрощение "как получилось", по нескольким
причинам:

1. Технические требования проекта (п. 5.2) прямо называют "дублирование
   данных для производительности" допустимой техникой — эта схема именно
   так её и использует.
2. Список регионов и боссов на сайте *всегда* читается целиком (нет
   сценария "показать один боссов без остальных его региона") — чтение
   одного документа вместо N+1 запросов к отдельным `bosses/{id}` и
   `regions/{id}` быстрее и не требует индексов для join'ов, которых в
   Firestore и вовсе нет.
3. Оба документа (`eldenring`, `shadowerdtree`) остаются маленькими
   (десятки боссов), поэтому лимит Firestore в 1 МиБ на документ не
   становится проблемой при таком объёме контента.
4. Реальное разделение на отдельные документы было бы оправдано, если бы
   бы боссов редактировали одновременно много разных людей (риск
   конфликтов записи) или если бы список боссов не помещался в один
   документ — ни то, ни другое не соответствует этому проекту.

## Оптимизация запросов

- Все публичные страницы и админ-панель используют `onSnapshot`, а не
  повторяющийся `.get()` по таймеру — это устраняет лишние запросы к
  Firestore и даёт живое обновление данных бесплатно.
- Клиентские SDK Firestore (Web/compat), в отличие от Admin SDK, **не
  поддерживают проекцию полей** (`.select()` есть только на сервере,
  в `firebase-admin`). Поэтому для `users` — единственной настоящей
  *коллекции* документов в проекте (а не одного документа-таблицы) —
  применена доступная на клиенте оптимизация: `orderBy('email')`
  переносит сортировку на сторону Firestore вместо браузера. Список
  аккаунтов при этом читается целиком, без пагинации — при типичном
  масштабе учебного/демонстрационного проекта (десятки, не миллионы,
  аккаунтов) это осознанный и адекватный выбор.
- Список регионов/боссов (каталог) вместо серверной пагинации использует
  клиентскую: 5 регионов на страницу с кнопкой "Показать ещё", поиск и
  сортировка — тоже на клиенте, поверх данных, уже загруженных через
  `onSnapshot`. Это не компромисс "не осилили серверные запросы", а
  прямое следствие пункта 1 выше: `gameData/eldenring` и
  `gameData/shadowerdtree` — это по одному документу на игру, а не
  коллекция из многих документов, поэтому `.limit()/.startAfter()`
  здесь просто неприменимы технически — делить один документ на
  "страницы" средствами Firestore-запросов нельзя, это можно сделать
  только на клиенте над уже полученными данными.
